### What problem does this code solve?

If you use a fixed INT32 for every length field, you always use 4 bytes regardless of the value:

```
value = 5    → 0x00 0x00 0x00 0x05  (4 bytes, 3 wasted)
value = 300  → 0x00 0x00 0x01 0x2C  (4 bytes, 2 wasted)
value = 5000 → 0x00 0x00 0x13 0x88  (4 bytes, 2 wasted)
```

Most lengths in Kafka are small numbers (< 127). Why waste 4 bytes every time?

Uses only as many bytes as needed:

```
value = 5    → 0x05         (1 byte)
value = 300  → 0xAC 0x02    (2 bytes)
value = 5000 → 0x88 0x27    (2 bytes)
```

### The idea: use bit 7 as a continuation flag

Each byte only uses 7 bits for data. Bit 7 (MSB) signals whether to keep reading:

```
bit 7 = 1 → "keep reading — next BYTE has more data"
bit 7 = 0 → "stop here — these 7 bits are the last chunk"
```

```
byte 1:  1 | 0 1 0 1 1 0 0
         ↑   ↑-----------↑
         │   7 bits of data (bits 0-6 of final value)
         continuation = 1 → "go read the next byte too"

byte 2:  0 | 0 0 0 0 0 1 0
         ↑   ↑-----------↑
         │   7 bits of data (bits 7-13 of final value)
         continuation = 0 → "done, this is the last byte"

final value = (byte2_data << 7) | byte1_data
```

When continuation = 0, the cursor moves to the next byte which starts a **new field** — nothing is skipped or wasted.

### LEB128 Unsigned — Encode & Decode

**Magic masks:**
```
0x7F = 0111 1111  → AND mask: keeps lower 7 bits, clears bit 7
0x80 = 1000 0000  → OR  mask: forces bit 7 to 1 (continuation flag)

They are exact opposites targeting the same bit:
  n & 0x7F  → isolate lower 7 bits (clear bit 7, so no accidental continuation flag in data)
  n | 0x80  → set bit 7 = "more bytes follow"
```

**Encode:**
```
while n >= 0x80:
    emit (n & 0x7F) | 0x80   // take lower 7 bits, force bit 7 = 1 (more bytes follow)
    n >>= 7                  // discard the 7 bits just emitted
emit n                       // last byte, bit 7 stays 0 (done)
```

In Go code this looks slightly different:
```go
for n >= 0x80 {
    res = append(res, byte(n)|0x80)  // byte(n) truncates to 8 bits — & 0x7F not needed
    n >>= 7                          // because | 0x80 forces bit 7 to 1 anyway
}
res = append(res, byte(n))           // last byte, no | 0x80 so bit 7 stays 0
```

`byte(n) | 0x80` vs `(n & 0x7F) | 0x80` — same result:
```
byte(n)          = xxxx xxxx   (lower 8 bits of n)
byte(n) | 0x80   = 1xxx xxxx   (force bit 7 to 1 — don't care what it was before)

(n & 0x7F)       = 0xxx xxxx   (clear bit 7 first)
(n & 0x7F)| 0x80 = 1xxx xxxx   (set bit 7 to 1)
```
Both end up as `1xxx xxxx`. The `& 0x7F` just clears bit 7 before `| 0x80` sets it back — redundant.
`byte(n) | 0x80` skips the clear step since you're forcing bit 7 to 1 anyway.

**Decode:**
```
result = 0
shift = 0
while true:
    b = read next byte
    result |= (b & 0x7F) << shift   // strip continuation bit, place 7 bits at correct position
    shift += 7
    if bit 7 of b == 0: break       // last byte, stop
```

To just check "is this 1 byte or 2 bytes?" (Kafka's shorthand):
```
(content[cursor] >> 7) & 1 == 0 → 1 byte
(content[cursor] >> 7) & 1 == 1 → 2+ bytes
```

### LEB128 Signed — Zigzag encoding

Negative numbers in two's complement are huge:
```
-1  = 1111 1111 1111 1111 1111 1111 1111 1111  (32 bits all 1s)
-2  = 1111 1111 1111 1111 1111 1111 1111 1110
```

Why takes 32 bits to store -1 and -2? Because the first bit is the sign bit. If it is 1 then it is negative, if it is 0 then it is positive. So we need to use 32 bits to store negative numbers.

Can we store -1 in 1 byte?

Encode (int -> zigzag)

```
encoded = (n << 1) ^ (n >> 31)
```

Left shift does not have the sign bit so it always follows Logical shift means shift every bit to the left 1 place
n << 1 doubles it (makes room for the sign bit) - 1111 1111 1111 1111 1111 1111 1111 1110

n >> 31 is all 0s for positive, all 1s for negative (arithmetic shift)

```
int, int32, int64 (signed) - Arithmetic shift (fill vacated bits with the sign bit): n >> 31 = 1111 1111 1111 1111 1111 1111 1111 1111
uint, uint32, uint64 (unsigned) - Logical shift (move every bits to the right 31 places): n >> 31 = 0000 0000 0000 0000 0000 0000 0000 0001
```

XOR flips the bits for negatives

```
  1111 1111 1111 1111 1111 1111 1111 1110   (n << 1)
^ 1111 1111 1111 1111 1111 1111 1111 1111   (n >> 31)
= 0000 0000 0000 0000 0000 0000 0000 0001
```

Decode (zigzag -> int)

```
n = (encoded >> 1) ^ -(encoded & 1)

encoded >> 1 = 0000 0000 0000 0000 0000 0000 0000 0001  >> 1
= 0000 0000 0000 0000 0000 0000 0000 0000

encoded & 1 = 0000 0000 0000 0000 0000 0000 0000 0001 & 1 = 1

-(encoded & 1) = -1

  0000 0000 0000 0000 0000 0000 0000 0000   (step 1)
^ 1111 1111 1111 1111 1111 1111 1111 1111   (step 3)
= 1111 1111 1111 1111 1111 1111 1111 1111
```

### The idea

Kafka is small so 8 bits is enough

They use MSB (bit 7th) to signal is there more byte after or not.

bit 7 = 1 → "keep reading next BYTE not next bit"
bit 7 = 0 → "stop here, take these 7 bits as the value"

```
byte 1:  1 | 0 1 0 1 1 0 0
         ↑   ↑-----------↑
         │   7 bits of data
         continuation = 1 → "go read the next BYTE too"

byte 2:  0 | 0 0 0 0 0 1 0
         ↑   ↑-----------↑
         │   7 bits of data
         continuation = 0 → "done, this is the last byte"
```
